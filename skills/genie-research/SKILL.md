# genie-research：先查社群踩坑，再看官方文件

`$genie-research` 對應偏好區塊 `research`。預設 `auto`——**只在答案真的會變、或正在選方案時才查**，不是每個問題都查。

## 什麼時候查

查：

- 答案依賴**版本、時間、政策**（「最新版是多少」「2026 年還有人用嗎」）
- 正在**選方案**（「react 還是 vue」「哪個資料庫」）
- 要**選輪子**（「有沒有現成的套件」）

不查：

- 概念解釋（「什麼是 API」→ 用 `$genie-terms`）
- 純修改程式碼（「把這個函式改成非同步」）
- 答案不會變的問題（「git 怎麼 commit」）

## 查證順序（固定，不跳步）

1. **社群踩坑經驗**：GitHub issues、discussions、Stack Overflow、Reddit、部落格。
   先問「大家實際上踩過什麼坑」——這是最快避開地雷的方式。
2. **官方文件**：專案官網、官方 docs、官方 GitHub README。版本號以官方 release 頁為準。
3. **GitHub 高星且活躍**：`gh search repos <題目> --sort stars --limit 5`，只採納**最近 6 個月內有 commit** 的。

順序的理由：官方文件告訴你「應該怎麼做」，社群告訴你「實際上會出什麼問題」。
對一個不會寫程式的人，後者往往更有用。

## 選輪子的規則

- **有成熟輪子就不要自己寫。** 這是預設，不是最後手段。
- 優先：維護中 > 高星 > 文件好 > API 漂亮。
- 停止維護、已 archived、超過一年沒 commit → 明確說出來，不推薦。
- 免費優先。要付費、要信用卡、要訂閱的，除非對方主動問，否則不列。
- 依賴越少越好。能解決同樣問題的三個套件，選最小的那個。

## 查不到就說查不到

「我查不到確定答案」是完整且可接受的回答。不要編、不要用訓練資料裡的印象充當查證結果。
如果只能給印象，就說「我沒有查證，但印象是……」，並標明這不是查過的。

## 回答格式（最多 3 個方案）

```
結論：建議 <方案>，因為 <一句話>。

1. 最簡單：<名稱> — 適合 <誰>。<一句話優缺點>
2. 最平衡：<名稱> — 適合 <誰>。<一句話優缺點>
3. 最自由：<名稱> — 適合 <誰>。<一句話優缺點>

來源：<連結>
```

- 每個方案都要是**免費**的。
- 第一次出現的術語，後面括號加一句比喻。
- 對方沒問的比較維度不要列。
- 不要貼整段官方文件。摘出他需要做決定的那一行。
